# UX_AUDIT — 邮箱聚合平台（v2.0）产品与 UI/UX 审查报告

> 审查日期：2026-07-15
> 审查对象：本地运行的 `server.js` + `public/`（原生 JS/CSS，无框架）+ Electron 桌面壳
> 审查方式：完整阅读前后端源码 + 用**空的临时数据库**（`OAUTH_IMAP_DB` 指向 `$TMPDIR`）启动真实服务，导入 3 个**虚构 `@example.com` 账号**观察真实界面。全程未读取、未展示 `data/` 中的真实凭证与邮件。
> 输出语言：中文

---

## 0. 一句话结论

产品的**真实身份是「多 Outlook 账号的 OAuth 凭证管理 + 邮件读取 + 验证码提取工具」**（由 `server.js`、`public/app.js` 与 `docs/superpowers` 的 spec 共同印证），而非通用邮箱客户端。它叫"邮箱聚合平台"，容易让人误以为是 Spark/Gmail 那类读写邮件的产品，但它有意做成**只读的凭证/验证码工具**——这本身是合理定位，不是缺陷。

因此本报告**按工具自身定位来评判**：核心问题不在于"缺少撰写/回复"（它本就不需要），而在于**作为一个凭证/验证码工具，它的信息密度、视觉层级、删除安全、状态反馈与效率还不到位**。三套 Demo 就是围绕这个真实定位做的高保真重设计。

> 说明：本报告最初把产品误判为"应当成为通用邮箱平台"，据此提出了"补齐统一收件箱/搜索/撰写"等建议。经与产品确认真实定位后，下方 P0-1/P0-3 已改为按"凭证/验证码工具"重新评判；涉及撰写/回复的部分不再视为缺陷。

---

## 1. 产品理解（实测 + 已确认）

| 维度 | 实际情况 |
|---|---|
| 真实定位 | 批量导入 Outlook/Hotmail 的 `email/client_id/refresh_token`，检测凭证存活，读取最近 3 封邮件并**自动提取验证码/验证链接**；refresh token 保活；网站标记 |
| 主要用户 | 管理**大量** Outlook 账号、频繁取验证码的运维/测试人员（重度用户） |
| 核心流程 | 导入凭证 → 账号列表看存活状态 → 点账号读最近 3 封 → 复制验证码 / 打开验证链接 → 定期保活、清理失活 |
| 数据来源 | 本地 SQLite；无 mock/demo 模式；看**界面**不需要连 IMAP，看**邮件**才需要 |
| 认证模型 | 无鉴权，仅靠绑定 `127.0.0.1` + CORS 限 localhost |

**核心矛盾**：它是一个**高频、重复、批量**的工具，但界面（超大标题、一屏 3 封摘要、串行刷新、裸 confirm 删除）却像个演示页，配不上"每天处理大量账号"的真实使用强度。这是所有 P1 问题的根源。

## 2. 问题清单

> 严重程度：P0 阻断核心价值 / P1 严重影响体验 / P2 明显但可绕过 / P3 打磨项
> 修改成本：低（<0.5 天）/ 中（0.5–2 天）/ 高（>2 天或涉及架构）

### 【产品与信息架构】

---

#### P0-1 命名与定位表达不清（但产品本身定位合理）

- **位置**：全局；`README.md` 标题"Outlook OAuth2 IMAP 内部测试工具" vs `package.json` productName "邮箱聚合平台"
- **证据**：README 自称"内部测试工具"，App 名与窗口标题却是"邮箱聚合平台"；界面无一处说明它是"凭证/验证码工具"。
- **用户影响**：新用户会误以为是通用邮箱客户端，进来找不到撰写/收件箱而困惑；名不副实损害信任。
- **推荐解决**：**不改变只读凭证/验证码工具的定位**，但统一表达——标题/副标题明确"多 Outlook 账号凭证与验证码工具"，首屏用一句话说明它能做什么（看账号健康、取验证码、清理失活）。三套 Demo 均已这样表达。
- **修改成本**：低
- **优先级**：高

---

#### P0-2 账号/邮件缺少查找能力

- **位置**：全局，无任何 `input[type=search]` 或含"搜索"占位符的输入框（实测 `hasSearchInput=false`）
- **证据**：全站按钮仅 13 个，无搜索/过滤入口；账号一多只能靠肉眼从列表翻找。
- **用户影响**：管理几十上百个账号时，定位某个账号（或某个来了验证码的账号）非常低效。
- **推荐解决**：账号列表即时过滤（按邮箱 / 网站标记 / 状态）；可选：跨账号验证码流。三套 Demo 均已实现过滤（C 还做了自然语言查询）。
- **修改成本**：中
- **优先级**：高

---

#### P0-3 验证码提取的可发现性与信息层级不足（核心功能未被突出）

- **位置**：`renderMessageCard` / `renderCodes`
- **证据**：验证码作为邮件卡片里的一个小 chip 呈现，混在最近 3 封邮件中；跨账号没有"验证码汇总"视图。而验证码提取恰恰是这个工具**最高频、最核心**的价值。
- **用户影响**：用户每次取码都要先点账号、再读到邮件卡片、再找那个 chip；批量取码场景（多个账号轮流收码）效率低。
- **推荐解决**：把验证码提升为一等公民——账号行/卡片直接标注"有验证码"，详情区置顶大号验证码卡（一键复制），并提供跨账号验证码流。三套 Demo 均已这样做（A 验证码卡、B 磁贴、C 分流泳道）。
- **修改成本**：中
- **优先级**：最高

---

#### P1-4 "账号切换"实为"逐个点击"，无多账号并列/统一视图

- **位置**：`renderAccountRow` → `data-select` 点击切换 `state.selectedId`
- **证据**：一次只能选中一个账号在右侧显示其 3 封邮件；账号来源仅靠左栏选中态区分，右侧详情区不重复标注来源。
- **用户影响**：在多个账号间比对/流转需要反复点击，效率低；符合"重度用户工作台"的多栏并列诉求缺失。
- **推荐解决**：提供统一收件箱（合并视图）+ 明确的账号来源标签（颜色/头像/域名徽章）。
- **修改成本**：中
- **优先级**：高

---

### 【交互与安全操作】

---

#### P1-5 危险的删除操作缺乏充分防护与撤销

- **位置**：`deleteAccountsByIds`（public/app.js:1191）、`deleteInactiveAccounts`
- **证据**：删除仅一个 `window.confirm` 文本框，确认后立即调用 `/api/accounts/batch-delete`；README 与代码均注明"不可撤销"。"删除失活"依赖启发式判定的失活集合，误判即误删。
- **用户影响**：一次误点即永久删除多个账号凭证，无回收站、无撤销、无二次输入确认。对高敏感数据是重大风险。
- **推荐解决**：①危险操作用自定义模态而非原生 confirm，展示将删除的完整清单；②提供"撤销"toast（软删除保留 N 秒/回收站）；③批量删除要求输入数量或勾选"我已确认"。
- **修改成本**：中
- **优先级**：高

---

#### P1-6 "等待验证码"是阻塞式轮询，反馈弱、开销大

- **位置**：`waitForCode`（public/app.js:1380）、`waitForVerificationCode`（server.js:1629）
- **证据**：默认等待 60s、每 3s 一轮，**每一轮都重新完整登录 IMAP + 取 3 封邮件**；等待期间前端只有一个"等待中"按钮态，无倒计时、无"已检查 N 次"、无法取消。
- **用户影响**：取码是最高频动作，但用户盯着一个没有进度的按钮等最多 60 秒，不知还要多久、也停不下来；后端反复重连开销大。
- **推荐解决**：①给倒计时 + "已检查 N 次"进度 + 取消按钮；②后端复用连接而非每轮重连；③找到验证码后高亮并自动复制（现已自动复制，可再强化视觉）。
- **修改成本**：中
- **优先级**：高

---

#### P1-7 全局阻塞式忙碌状态，长耗时操作体验差

- **位置**：`state.busy / batchBusy / accountBusy` 等大量布尔位；`refreshAllAccounts` 串行 `for` 循环
- **证据**：批量刷新逐账号串行，每账号超时上限 95s（public/app.js:1462）；保活后端串行、每账号间隔 250ms（server.js:1771）。刷新期间大量按钮 `disabled`。
- **用户影响**：账号多时界面长时间"半锁死"，用户不知还要等多久，无法在等待时做别的事。
- **推荐解决**：并发刷新（限流并行）；用进度条 + 每账号独立状态而非全局锁；允许取消。
- **修改成本**：中
- **优先级**：高

---

#### P2-8 每次只取最近 3 封，且无法翻页/加载更多

- **位置**：`refreshAndFetch` 硬编码 3（server.js:1608）
- **证据**：验证码轮询也只在这 3 封里找（server.js:1629）。
- **用户影响**：错过第 4 封起的邮件；验证码若不在最新 3 封会漏抓。
- **推荐解决**：可配置抓取条数 + "加载更多"；验证码场景按时间窗口而非固定条数。
- **修改成本**：中
- **优先级**：中

---

### 【状态与反馈】

---

#### P2-9 错误信息直接透传原始报文，且状态码靠中文文案匹配

- **位置**：错误卡片 `renderMessageCard`（from==="Error"）；`apiErrorStatus` 按中文串关键词判 HTTP 码（server.js:141）
- **证据**：读取失败时把 `error.message`（可能含原始 IMAP/AADSTS 报文）塞进一条伪邮件卡片展示。
- **用户影响**：普通用户看不懂原始报错；"按文案判状态码"脆弱，改文案就可能改错状态码。
- **推荐解决**：错误分类映射为用户可读文案 + "查看技术详情"折叠；状态码用结构化错误类型而非文案匹配。
- **修改成本**：中
- **优先级**：中

---

#### P2-10 加载态信息化不足、无骨架屏，空状态可引导性弱

- **位置**：`renderMessages` 的 `.loading-box`；`renderEmptyPanel`
- **证据**：加载只有一个 spinner + 文案；空状态文案"展开账号操作添加账号后，选择一个账号读取邮件"要求用户先理解"账号操作"藏在右上角齿轮里。
- **用户影响**：首次使用者不易发现"如何添加第一个账号"；加载缺乏进度感。
- **推荐解决**：空状态给明确 CTA 按钮（"添加第一个账号"）；列表加载用骨架屏。
- **修改成本**：低
- **优先级**：中

---

#### P2-11 授权失效（invalid_grant）状态未形成清晰的"修复引导"闭环

- **位置**：`accountLifeStatus` 归类 error/inactive；后端对 AADSTS terminal 错误标记
- **证据**：失活账号在列表标红显示原因，但"如何重新导入最新 refresh token"没有就地的操作入口，用户需自己回到导入框重贴。
- **用户影响**：授权过期后修复路径长，容易放弃。
- **推荐解决**：失效账号行内提供"重新导入/更新凭证"按钮，直达预填该账号的导入流程。
- **修改成本**：中
- **优先级**：中

---

### 【视觉与设计系统】

---

#### P1-12 视觉层级失衡：标题与顶栏过大，信息密度过低

- **位置**：`.brand h1 { font-size: clamp(34px,4vw,56px) }`（实测 56px）；`.topbar { min-height:124px }`；`.selected-email-copy` 最大 40px；`.message-subject` 最大 34px
- **证据**：实测顶栏高 124px、主标题 56px；桌面首屏账号列表被挤压，右侧大量留白（见空状态截图）。移动端标题"邮箱聚合平台"换行成两行（见移动端截图）。
- **用户影响**：对一个以"密集管理大量账号"为核心的工具，超大标题浪费首屏、拉低信息密度，与用户任务背道而驰。
- **推荐解决**：主标题降到 20–24px，顶栏 56–64px，把节省的空间给账号列表与邮件内容。
- **修改成本**：低
- **优先级**：高

---

#### P2-13 全站"新拟物/硅胶"风格过重，可读性与对比度受损

- **位置**：`styles.css` 大量多层 `box-shadow`、渐变、`inset` 阴影（`--shadow`、`--soft-shadow`、`--field-shadow` 等）
- **证据**：按钮、输入框、卡片、徽章几乎都叠加内外阴影与渐变；`--muted:#647086` 在浅渐变背景上对比度偏低。
- **用户影响**：软阴影削弱了"可点/不可点"的边界；长时间高密度使用视觉疲劳；弱对比文字不利可访问性。
- **推荐解决**：保留一种克制的层次表达（单层阴影或 1px 边框），提高正文/次要文字对比度到 WCAG AA。
- **修改成本**：中
- **优先级**：中

---

#### P2-14 完全没有深色模式

- **位置**：`:root { color-scheme: light }`，全站 0 处 `prefers-color-scheme`
- **证据**：实测 CSS 无任何深色适配；邮件正文 iframe 也写死 `color-scheme: light`。
- **用户影响**：重度用户长时间使用、夜间使用缺乏深色选项。
- **推荐解决**：引入 CSS 变量驱动的浅/深主题（Demo A 提供深色）。
- **修改成本**：中
- **优先级**：中

---

### 【无障碍与响应式】

---

#### P2-15 无键盘快捷键，列表项焦点/键盘导航不完整

- **位置**：`bindEvents` 仅绑定 click/change，无 keydown 快捷键；账号行是可点 `<button>` 但列表无方向键导航
- **证据**：无 `keydown` 监听；重度工具却无 `j/k`、`/` 搜索、`e` 归档等键盘操作。
- **用户影响**：任务要求的"键盘操作/无障碍体验"缺失；重度用户效率上限被限制。
- **推荐解决**：Demo A 提供键盘导航与快捷键；补全 `aria-live`、可见焦点环（部分已有 `:focus-visible`）。
- **修改成本**：中
- **优先级**：中

---

#### P2-16 移动端信息架构未真正适配

- **位置**：`@media (max-width:860px)` 仅做单列堆叠
- **证据**：移动端顶栏标题换行两行、齿轮按钮孤立在左下（见移动端截图）；账号操作面板在移动端展开后极长。
- **用户影响**：移动端仅是"桌面缩窄"，非为触屏重新设计；关键操作触达深。
- **推荐解决**：移动端用底部导航/抽屉、更紧凑的账号卡片、把主操作提到可达区域。
- **修改成本**：中
- **优先级**：中

---

### 【工程与维护】

---

#### P2-17 根目录 `app.js` 是未被引用的冗余副本

- **位置**：`/app.js` 与 `/public/app.js`
- **证据**：两文件字节完全相同（均 1519 行 / 54597 字节）；`index.html` 只引用 `/public/app.js`，静态服务目录是 `public`，根目录不在服务范围。
- **用户影响**：（对开发者）日后只改其中一份会造成困惑与不一致。
- **推荐解决**：删除根目录 `app.js`（属于产品自身清理，本次不擅自删除，仅记录建议）。
- **修改成本**：低
- **优先级**：中

---

#### P3-18 无鉴权 + 本地"打开链接/重启"能力的信任表达不足

- **位置**：`/api/open-private`、`/api/open-link`、`/api/restart`
- **证据**：无鉴权，仅 localhost 绑定；HTML 邮件虽已消毒，但"精选链接/自动打开"逻辑存在被诱导打开钓鱼链接的可能。
- **用户影响**：安全模型对用户不透明；用户不清楚"点这个链接会不会有风险"。
- **推荐解决**：打开外部链接前显示目标域名确认；界面明示"本工具仅本机可访问、不上传数据"。
- **修改成本**：低
- **优先级**：低

---

#### P3-19 隐私/安全信息未在界面表达

- **位置**：全局
- **证据**：界面无任何"数据仅存本地/不外传/凭证如何保管"的说明。
- **用户影响**：处理高敏感凭证的工具，缺乏安全承诺表达，降低信任。
- **推荐解决**：设置页或首屏加一段简明安全说明。
- **修改成本**：低
- **优先级**：低
